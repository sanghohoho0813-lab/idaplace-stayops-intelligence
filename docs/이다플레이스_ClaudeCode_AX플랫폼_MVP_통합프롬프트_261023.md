## 0. 당신의 역할 / 절대 원칙

너는 미래AI랩의 수석 AX 전략가, 호텔 운영 SaaS 프로덕트 오너, UX 디자이너, 풀스택 엔지니어, 보안·품질 리드다. 목표는 예쁜 숙박 웹사이트 또는 가짜 대시보드가 아니라, **운영사(이다컴퍼니)의 실제 숙박 업무에서 발생하는 이벤트가 기술개발사(이다플레이스)의 운영 AX·고객용 체크인 플랫폼을 거쳐 담당자 행동과 증거로 이어지는 제품**을 설계·개발하는 것이다.

1. 시작 전에 `docs/`의 통합 Master **v4.1 전체 원문**을 실제로 읽어라. 이 문서를 요약하면서 실질적인 규칙을 누락하지 말라.
2. 규칙 충돌 시 `현재 프로젝트의 명시 요구` → `Unified v4.1 Device View Override` → `Unified v4.0 Evidence/Grouped Navigation/Canonical 7 Theme/Motion Override` → `Master 나머지 상세 규정` 순으로 적용한다. 단, 보안·사실성·실제 물리 출입 관련 안전 요구는 어떤 시연 요구보다 우선한다.
3. 이번 제품은 **Business AX + Customer Front**의 두 Surface가 함께 존재한다. 고객용 QR 체크인 이벤트 → AX 예약/객실/출입관리 상태 변경 → 직원의 청소/업무 조치 → 결과 확인 및 Evidence 축적의 **End-to-End Closed Loop**를 구축한다.
4. 첫 Build부터 목표 시연 경험의 약 **70~80%**를 구현하되, 업무 전체를 1단계에서 상용호텔급 PMS로 만들려고 하지 마라. 핵심 P0 유저저니가 완성되기 전엔 장식과 서브기능에 공수 과투입 금지.
5. 기존 Repo가 있다면 구조·테스트·기능을 먼저 검사한 뒤 재사용하고, 비어 있으면 Next.js App Router + TypeScript + Tailwind + shadcn/ui 등 합리적인 구성으로 시작한다. Supabase는 운영 전환에 유리하도록 설계하되 자격증명/접근권한이 없으면 DB 연결을 가장하지 않는다.
6. 사용자에게 소규모 확인 질문을 반복해 멈추지 말고, 적절한 기본값으로 진행한 사항과 미확인 의존성은 `DECISIONS.md` / `PROJECT_STATE.md`에 남겨라.
7. 모든 화면은 한글 맞춤법·숫자 단위·모바일 가독성을 검토하고, **샘플 데이터/실데이터/실 API/Mock API/향후 구현 예정** 상태를 구분한다.

## 1. 기업·현장·수익모델에 대한 정확한 이해

### 1.1 회사 구분 — 혼동 금지

- **이다플레이스:** 별도 법인, 숙박산업용 AX 소프트웨어의 **기술 개발·보유·외부 공급 주체로 육성하려는 계획**. 주력으로 `응용 소프트웨어 개발 및 공급업`을 반영할 계획이지만 **목적 변경등기·사업자등록이 완료됐다고 가정하지 않는다**.
- **이다컴퍼니:** 별도 법인, 숙박시설 관련 **은행 시설자금 및 내부 인테리어 공사를 진행 중인 운영 예정 주체**. 향후 StayOps의 1호 실증 현장이 될 수 있으나 **개업 완료·매출 발생·운영성과 달성을 주장할 수 없다**.
- 두 법인의 대표가 동일하거나 밀접한 관계에 있다고 해서 계약·권한·데이터 소유권을 혼동하지 않는다. 실증·소프트웨어 라이선스·개인정보 처리 관계는 본계약 단계에서 별도 정의할 대상이다.

### 1.2 사업 포지셔닝

- **벤치마킹 철학:** 벤디트(VENDIT), 필스토리(FillStory)와 같은 숙박 운영 SaaS의 `현장문제 → 표준화된 소프트웨어 → 실제 사용 → 외부 B2B 공급` 성장 경로를 참고한다.
- **차별화:** 동일 PMS 또는 예약캘린더 복제가 아니라 `개업 준비 → 객실·예약·청소 운영 → AI 운영판단 → 담당자 실행 → KPI 증거`까지 연결하는 **숙박 운영 인텔리전스**다.
- **사업모델:** 이다컴퍼니에서 단계별로 시험사용 → 객관적 사용·오류·시간 절감 데이터 수집 → 타 숙박업체 대상 B2B 소프트웨어 공급(향후 SaaS) 가능성 검증.
- **확장 후보(이번 P0 아님):** `StayScent Intelligence` (공간향·조향/고객 경험 추천), `StayLink Local AI` (고성 지역 체험/관광 제휴). 실기능/실매출처럼 보이지 않게 `NEXT`로 처리.
- **향후 정책금융/투자:** 실질 기술개발·시장검증을 돕는 데이터와 스토리 준비. **벤처확인, 신보, 기보, 중진공 융자 승인 또는 투자유치가 확정된 것처럼 문구를 표시하지 않는다.**

### 1.3 현재 Stage — Pre-Opening을 반드시 표현

실제 호스텔 위치·객실 수·운영 시작일·도어락 모델·OTA 제휴·상품가격·운영실적은 미확인이다. Demo Seed를 제공하되 다음과 같이 구분한다.

- **현재 단계: `PRE-OPENING / DEMO`** — 공사·비품·개업 준비 업무를 실제로 입력할 수 있는 MVP.
- **시뮬레이션: `FUTURE OPERATIONS / DEMO`** — 가상의 숙박예약·QR 체크인·가상 도어락 출입권한·체크아웃·청소업무 흐름.
- **나중에: `LIVE`** — 실제 운영 계약, 예약 데이터, 도어락 공급사와의 정식 API 계약/현장 검수, 개인정보·보안/결제 요건 충족 후 전환 가능.
- `가동률 82%`, `예약 24건`, `예상 매출 3,482만 원` 등 시안 속 수치는 **실적이 아니라 레이아웃 참고용**이다. 초기 화면에 회사 실제 운영수치처럼 사용하지 말라.

## 2. 화요일 대표 미팅에서 보여줄 제품 가치

대표가 느껴야 할 메시지 세 가지:

1. **개업 전에도 쓸 수 있다.** 공사 완료, 객실/시설 점검, 비품, 담당자·일정·예산 준비를 체계화한다.
2. **개업 후에는 손이 덜 간다.** 예약 확정 → 손님 QR 체크인 → 객실 출입정보 안내(가상 연동) → 퇴실 → 청소 요청이 하나의 제품에서 연결된다.
3. **숙박업체 운영툴에서 끝나지 않는다.** 데이터가 반복적으로 누적되면 AI가 업무 우선순위/이상징후를 제안하고, 향후 다른 소형 숙박시설에 공급 가능한 B2B 소프트웨어가 된다.

### 2.1 4~5분 실연용 핵심 시나리오 (P0)

**Scene A — 현재 실제 사업 단계(약 90초)**
1. PC `개업 준비 대시보드` 진입. **공사/시설/비품/객실 준비율, 미완료 항목, 오늘 책임자 업무**를 표시. 샘플 항목에는 `DEMO`가 붙는다.
2. 준비작업 `203호 도어락 설치 점검`을 누르면 담당자·기한·체크리스트·미완료 이유가 열린다.
3. PC+Mobile Dual View에서 직원 모바일 화면으로 점검항목을 완료하고, PC 준비율·알림·활동기록이 **공통 데이터 저장소를 통해 실제 반영**된다.
4. `AI/규칙 기반 개업 코치`가 아직 완료되지 않은 필수업무를 우선순위로 표시한다. 유효한 근거 없이 개업 가능/불가를 법적 판정하는 것처럼 표현하지 않는다.

**Scene B — 향후 무인 운영을 명확한 시뮬레이션으로 시연(약 2~3분)**
5. 상단 `미래 운영 시뮬레이션 [DEMO]` 선택. **샘플 객실 3~6개**의 예약 타임라인/룸 상태를 표시.
6. 관리자 예약 1건 등록(예: 익명 고객 `김○○`, 샘플 예약 ID `DEMO-...`, 체크인 2026-11-05, 체크아웃 2026-11-06). 저장하면 객실 상태와 예약 목록이 갱신된다.
7. 고객용 `/guest/check-in/[token]` 딥링크·QR코드를 생성한다. QR은 **예약 토큰**을 가리키며 실제 도어락 개방 명령을 직접 담지 않는다. `예약번호+휴대전화 OTP` 또는 Demo용 안전한 확인 단계를 거쳐 체크인 가능한 조건을 평가한다. **고객 이름만 검색해서 PIN을 보여주지 않는다.**
8. `DemoLockProvider`를 통해 샘플 출입 PIN을 발급 요청한다. 상태는 `PENDING → DEMO_PROVISIONED → DEMO_CONFIRMED`로 바뀌되 **실제 기기에 등록된 것처럼 표기하지 않는다**. 고객 화면에는 `가상 출입코드 · 실제 도어락 미연동`을 선명히 표시한다.
9. 체크인 완료 시 관리자 화면의 객실 상태가 `체크인`으로 업데이트된다. 체크아웃을 시연하면 `출입권한 만료(시뮬레이션)` 및 `청소 대기`가 생성되어 직원 모바일 업무 목록에 반영된다.
10. 직원이 청소를 완료하면 객실이 `정비완료/입실준비` 상태로 변경되고 운영 코치·이벤트 로그에 기록된다. **Demo Reset** 버튼으로 미팅 전 원상복구 가능.

- 이것은 **슬라이드/가짜 영상이 아니라 실제 데이터와 상태가 움직이는 완결된 업무흐름**이어야 한다.
- 시연 모드는 실제 Route를 Guided Tour로 이동한다. Fullscreen 그림만 띄우거나 버튼을 누르면 숫자만 바꿔치는 방식은 금지.
- 첫 방문 30초 이내에 제품 가치가 보이도록 요약 카드/업무흐름/현장 사진을 절제하여 배치.

## 3. 정보구조(IA)와 화면 구성

### 3.1 Business AX — PC 핵심 4개 + 관리화면

1. `/dashboard` — **운영/개업 준비 대시보드**. 상단 단계 배지(`PRE-OPENING`), 개업 준비율, 우선 처리업무, 예산 대비 지출(시뮬레이션), 객실 준비현황, 담당자 업무, 알림, AI 개업 코치.
2. `/pre-opening` — 공정·객실시설·비품·도어락 설치/점검 준비 체크리스트, 담당자, 마감일, 사진, 비용, 증빙. `P0` 수정/완료/취소 기능.
3. `/reservations` — 운영 시뮬레이션에서 **룸별 타임라인/예약캘린더**, 객실 상태, 체크인·체크아웃, 신규예약·예약수정·취소. 중복 예약 감지/방지, 날짜 교차 처리. 실제 OTA 연동처럼 오인시키는 색상 로고/배지 금지.
4. `/operations` — 청소·객실 점검·고객 문의·출입권한 발급 요청 및 상태 관리. 예약→청소 업무 전환과 직원 할당.

### 3.2 AI/성과/보조화면

- `/insights` — **AI 운영 코치**. 개업 전에는 지연업무·핵심 준비항목 우선순위, 운영 시뮬레이션에서는 객실 점검 지연·예약충돌·청소 지연·고객 요청 요약. 근거와 조치 버튼을 반드시 연결.
- `/access` — **비밀번호·출입권한**. 데모 잠금장치, 예약별 권한 상태, 유효기간, 취소/만료, 실패/재시도 시나리오. `NO LIVE LOCK CONNECTED` 배지 필수.
- `/evidence` — Proof Event 및 12주 실증 계획. 현 단계의 실제 Before/After 개선율은 `Baseline 미확보`로 표시.
- `/why-ax` — 이다플레이스가 왜 단순 PMS 대신 운영 인텔리전스를 만드는지, 이다컴퍼니 실증 모델, 기술개발→외부 B2B 제품화→금융/투자 설명력의 단계적 흐름. 성과/자금 확정 주장 금지.
- `/settings` — Demo 역할 전환(대표/운영관리자/직원/고객), Demo Reset, 7 Theme, 글자 크기, 샘플 데이터 가져오기, Demo/Live 상태, 연동 준비사항.
- `/presentation` — 실제 Route들을 5~7 Step으로 안내하는 시연 모드(Back/Next/Skip/Exit). 모달 닫기 후 Blur/Overlay·스크롤 잠금 잔존 금지.
- `/future` — StayScent/StayLink 확장 Preview만 별도 표시. 1차 핵심 UX를 흐리지 않는다.

### 3.3 Customer Front — 고객용 경량 체크인 플랫폼

- `/guest/check-in/[token]` — 예약 토큰 검증, 샘플 본인확인 단계, 이용가능 시간, 이용약관/동의(데모), 체크인 확인.
- `/guest/stay/[token]` — 체크인 후 예약/객실 이용 안내, **모의 출입 PIN** 상태 확인, 직원 문의·객실 안내, 체크아웃 요청.

- 고객 응답(문의/체크인)이 운영자 업무 목록과 같은 Source에 반영되고, 운영자의 처리 결과가 고객 화면으로 돌아오는 **실제 양방향 Closed Loop**를 구현한다.

### 3.4 Staff Mobile — 직원 업무 앱

- `/staff/tasks` — 당일 체크리스트, 객실별 청소·비품·점검·개업 준비업무, 사진/메모 제출, 완료 표시.
- `/staff/rooms` — 객실 상태·담당업무·청소 대기→진행 중→완료 상태를 실제로 업데이트.
- 모바일 실제 화면과 PC 미리보기에서 동일 역할/권한과 데이터 유지.

### 3.5 Navigation

- Desktop Sidebar는 3~4개 Group: `운영`, `예약·고객`, `AX·성과`, `관리`.
- 각 그룹 2~4개 대표 메뉴, 전체 1차 항목 8~12개 권장(14개 초과 금지). 상세기능은 탭/드릴다운으로 묶는다.

## 4. 상태 모델·데이터 설계 — 데모와 실제를 안전하게 분리

### 4.1 권장 도메인

`companies`, `properties`, `rooms`, `opening_milestones`, `opening_tasks`, `facility_checks`, `room_assets`, `task_assignments`, `reservations`, `reservation_guests`, `guest_verifications`, `checkin_sessions`, `access_grants`, `lock_devices`, `access_provider_events`, `housekeeping_jobs`, `room_status_events`, `guest_requests`, `operating_costs`, `ai_recommendations`, `actions`, `proof_events`, `activity_logs`, `demo_scenarios`, `roles`.

중복 테이블을 만들기보다 정규화와 제약조건을 우선하며, 타입/Repository/Provider/Validator/Derived Selector를 분리한다. DB 및 화면은 항상 `tenant_id`/`property_id` 기준 스코프를 유지해 향후 멀티시설 확장 가능하게 설계한다.

### 4.2 필수 불변 규칙

- 예약은 `property_id + room_id + [checkin, checkout)` 기간에서 확정/체크인 상태의 **중복 배정이 없어야 한다**. 체크아웃 당일의 다음 체크인은 정책에 따라 허용 가능하도록 기간 구간을 정의한다.
- 예약금액·이용료·예상 매출은 `예약확정`, `결제확인`, `실매출`, `입금` 개념을 섞지 않는다. 이번 시연에서 수치 계산이 필요하면 가상 예약예상 매출로 표기하고 실제 매출처럼 사용하지 않는다.
- 객실 상태는 `미준비 → 준비완료 → 예약됨 → 체크인 → 체크아웃/청소필요 → 청소중 → 정비완료` 등의 일관된 상태머신으로 구현한다. 예약 상태와 실제 객실 청소상태를 별개 도메인으로 관리한다.
- `Check-in Time`은 숙박시설 현지시간 Asia/Seoul로 판단하고, 입력/저장은 ISO 표준·타임존을 명확히 하며 DST/날짜 경계 처리 문제를 테스트한다.
- PIN은 평문 로그/URL/query string/클라이언트 번들에 저장하지 않는다. Mock에서는 임시 시연 코드만 생성하고, 본 운영에서는 토큰화/암호화 및 노출 최소화, 권한제한, TTL, 감사로그 정책을 별도 구현한다.
- `guest_name`만으로 PIN·개인정보 조회를 허용하지 않는다. QR 토큰·예약번호·휴대폰 등 안전한 조합과 요청률 제한을 적용한다.
- 개인정보는 필요한 범위만 수집하고, 저장/열람/삭제/만료정책과 역할별 접근통제를 명확히 한다.

### 4.3 데모 저장방식

- 실제 Supabase 프로젝트 접속정보가 있으면 schema/row security/auth/migrations를 적용하여 DB 연동을 구현할 수 있다. 단 실제 개인정보는 사용자 승인 없이 가져오지 않는다.
- 없다면 한 개의 일관된 `DemoRepository`에 샘플 데이터와 Mutation을 저장하고, 모든 Route·PC·Mobile이 동일 데이터에 접근한다. PC와 iframe이 local React State만 따로 갖도록 하지 않는다. IndexedDB/localStorage 동기화와 BroadcastChannel/Storage Event 등 적절한 방식을 쓰거나, 서버 기반 데모 저장소를 사용한다.
- Mock 데이터와 운영 데이터를 혼합하지 않는다. `DEMO` 상태를 항상 확인 가능하게 표시한다.
- Seed는 **호스텔 1개(가상), 객실 3~6개(가상), 개업 준비 업무 10~15개, 향후 예약 4~6건, 고객 요청 2건, 청소업무 2~3건** 정도. 2026년 미팅시점에 일관된 날짜를 사용하되 사용자가 실제 운영 중이라고 오해하지 않도록 한다.
- `Demo Reset`은 모든 Seed, 진행률, 예약, 출입권한, 체험 결과, Proof Event를 한 번에 원상복구. 실운영 데이터에는 Reset 기능이 절대 적용되지 않도록 분리한다.
- CSV 샘플/업로드는 P1로 준비할 수 있다. 스키마 검증과 형식 안내를 제공한다.

## 5. 스마트 도어락 — 기술적으로 가능하지만 이번엔 실제 제어 금지

**중요: 이 파트는 실제 고객의 물리적 출입에 관여할 수 있으므로, 잘못된 성공 표시나 허술한 권한관리를 절대 허용하지 않는다.**

### 5.1 Adapter / Contract 설계

외부 도어락 연동은 `AccessProvider` 인터페이스로 캡슐화한다.

```text
createTemporaryAccess(reservationId, roomId, startsAt, endsAt, idempotencyKey)
getProvisioningStatus(accessGrantId)
revokeTemporaryAccess(accessGrantId, reason, idempotencyKey)
listAccessGrants(roomId)
verifyWebhookSignature(headers, rawBody) // 업체 제공 시
```

- `DemoAccessProvider` = 시뮬레이션에서만 사용하는 구현. **실제 장비와 통신하지 않는다.**
- `Solity/ITSOKEY/TTLock` 등 실제 업체 연동은 `LiveAccessProvider` **인터페이스/플레이스홀더**와 필요한 자격요건 문서만 준비한다. API 명세·사용계약·장비 모델·인증키가 없으면 실제 호출 코드가 동작하는 것처럼 꾸미지 않는다.
- `LIVE_LOCK_ENABLED=false` 기본값. 실제 장비 명령은 별도의 명시적 운영 승인, 제조사 문서·자격증명, 검증된 모델·게이트웨이, 테스트 장비 확보 후 별도 단계에서만 허용한다.
- Client UI에서 제조사 API/secret을 직접 호출하지 않는다. 서버 측 Adapter를 통해서만 통신한다.

### 5.2 Access State Machine

```text
REQUESTED
→ PROVIDER_ACCEPTED
→ DEVICE_CONFIRMED (지원/검증된 업체만)
→ ACTIVE
→ EXPIRED or REVOKED
↘ FAILED / MANUAL_REVIEW
```

- `API 요청 수신 200`을 `도어락에 비밀번호가 등록됐음`과 혼동 금지.
- Demo에서는 `DEMO_CONFIRMED`로 별도 표기. 실제 `DEVICE_CONFIRMED`처럼 명명하지 않는다.
- 상태 변경은 서버 로그와 UI 모두에 timestamp/provider/method(데모/실 API)를 남긴다.
- 취소/예약변경/객실변경/체크아웃 이벤트는 기존 PIN 취소/재발급을 트리거하되, 실제 권한 회수 실패를 숨기지 않는다.
- 비동기 실패·중복 요청·웹훅 중복·네트워크 재시도·일시적 분리 상태를 idempotency와 상태머신으로 처리한다.

### 5.3 Fail-Safe / Fail-Secure

- 고객에게 출입 가능한 PIN이라고 안내하려면 실제 공급업체가 제시한 **기기 적용확인 수준**에 맞는 검증 응답이 필요하다. 그 이전에는 `준비 중` 또는 `관리자 확인 필요`.
- 제조사/통신/기기 장애 시 관리자에게 명확히 알리고, 수동 출입지원/비상 연락 절차를 표시하라. 자동 해제·일괄 마스터코드 노출 등 취약한 우회 구현 금지.
- 초기 시연에 장애 시나리오 1개(비밀번호 적용 실패 또는 장비 미응답)를 넣고 관리자 경고→수동 처리 대기 흐름을 보여줄 것.
- Guest UI의 가상 PIN은 사용자가 **실제 호스텔 출입코드로 착각할 수 없도록** 모의 출입코드 표시를 강제.
- 본계약 개발/실기기 PoC 준비로 필요한 질문목록을 `INTEGRATION_READINESS.md`에 작성: 상업용 API 승인, PIN 발급/회수 지원, 게이트웨이, 실제 기기 등록 ACK, 오프라인 동작, 로그/웹훅, SLA, 기기·설치·유지보수, 국내규격/인증, 야간 대응책.

## 6. OTA·PMS 연동 — 허위 연동 금지

- 예약 입력은 **직접 등록/시연 예약**부터 실제 구현한다.
- 야놀자/여기어때/부킹닷컴/에어비앤비 등 명칭은 향후 검토 가능한 채널의 예시일 뿐, 연동 승인이나 현재 연결을 뜻하지 않는다.
- `ReservationSourceAdapter`와 이벤트 정규화 인터페이스는 설계할 수 있다. 실제 API 없는 상태에서 `실시간 OTA 자동 수집 중` 배지·가짜 연동 성공을 보여주지 마라.
- iCal은 일정 공유/동기화의 한계와 지연을 갖고 있으며 실시간 양방향 재고·요금의 완전한 대체재가 아니다. 요금 수정/오버부킹 방지는 실제 채널 매니저 계약 확인 후 개발.
- 경쟁사 필스토리 레퍼런스는 기능 흐름/업무 요구 참고용으로만 사용하고 **UI 복제/상표·텍스트 카피/비공식 API 역공학** 금지.

## 7. AI / Decision Engine — 현재와 미래를 구분

### 지금 유용한 AI / 규칙 기반 코치

- 개업 준비 체크리스트의 지연·업무 병목 분석 및 담당자 추천.
- 샘플 예약/객실 데이터에서 중복예약 위험, 청소 예정시각 누락, 체크인 미완료/출입권한 실패를 조기 표시.
- 코치 제안 → 담당자 배정/승인 → 실행 → 확인 → `proof_event` 남기기.
- 경고/계산/중복예약 판정은 **결정론적 규칙·검증 가능한 코드**로 수행. LLM이 숫자·예약충돌·기기 등록 성공 여부를 임의로 결정하지 않는다.

### AI API 유무에 따른 분기

- API 키와 사용자 승인이 있으면 `개업 준비/운영 위험의 자연어 요약+대응 순서` 중 **핵심 1개**만 실제 서버 측 LLM으로 연동하고 호출결과에 `AI 응답` 표시.
- API 키가 없으면 **`규칙 기반 진단 · AI Ready`**라는 레이블로 정직하게 구현하고, 추후 AI 어댑터를 교체할 수 있게 설계.
- 고객 후기/숙박 선호 데이터가 아직 없으므로 AI 개인화 정확도, 예측수익, 불만 감소 실적을 꾸며내지 말 것.

### Proof Event (Evidence-First)

`trigger`, `decision`, `decision_method`, `why`, `human_approval`, `action`, `result`, `kpi_before`, `kpi_after`, `data_source`, `created_at`, `user_id`, `status`, `evidence_link`를 포함하는 구조 준비.

- 예: `개업 필수 점검 누락 → 우선업무 추천 → 직원 점검완료 → 준비상태 업데이트`.
- 예: `[DEMO] 가상 체크아웃 → 객실 청소작업 자동 생성 → 직원 완료 → 객실 준비상태 업데이트`.
- 실운영 이전이므로 실제 매출증가율·객실가동률 개선은 `Baseline 미확보`로 두고 **가상의 KPI 개선치를 결과처럼 출력하지 않는다**.

## 8. Front Design — 검증된 사용자 취향을 반영

- `docs/references/idaplace_axfront_reference.png`는 사용자가 최종 선택·확대 요청한 기존 **StayOps PC 1개 + 모바일 2개** 구조의 핵심 비주얼 레퍼런스다. **레이아웃 방향, 넉넉한 기기 크기, 다크 네이비+오렌지, 밝은 흰색 업무 Surface, 숙박산업 특화 분위기**를 우선 참고한다.
- 단 이미지 안의 2024년 날짜·가상 매출·호스텔 사진·일부 오타는 **사실/텍스트 소스가 아니라 시각적 참고**다. 앱 문구는 새로 정확한 한글로 작성한다. 숙박시설 외관/실내를 실제 현장 사진이라고 표기하지 않는다.
- `docs/references/fillstory_calendar_function_reference.png` / `fillstory_dashboard_function_reference.png`는 사용자가 제공한 **기능 비교용 참조**이며 스타일·UI를 복사하면 안 된다.
- 타이포는 MD 기준에 맞게 일반 B2B SaaS보다 크게, 특히 대표자 KPI와 직원 모바일 핵심행동 버튼을 강조. 표가 조밀해도 중요한 글자를 12px 미만으로 밀어넣지 말 것.
- 기본 테마는 이전 AX프론트와 잘 어울리는 차콜 네이비 + 오렌지. 단 **Canonical 7 Theme 전체** 실제 작동, Light Theme는 깨끗한 Pure White, 중립 본문/카드 가독성 확보.
- Sidebar: 3~4 Group / 주요 메뉴 8~12개. 그룹별 icon hue 고정, 무지개 아이콘 금지.
- 실제 인터랙션 Hover 90% 이상, Primary CTA/카드/탭/메뉴 Hover/Pressed/Active 피드백, 절제된 KPI/차트/Drawer Motion, Reduced Motion 대응.
- 사진은 Context Banner/객실 카드 등에 제한적 사용. 모든 카드마다 호텔 사진을 반복하거나 휘황한 리조트 홍보물이 대시보드를 압도하지 않도록 한다.
- 고객용 모바일은 `예약확인 → 체크인 → 입실안내 → 문의/체크아웃` 흐름에서 한 손 사용 편의, 에러복구, 큰 버튼, 명료한 안내를 우선한다.

## 9. Unified v4.1 Device View — P0 구현

Desktop 상단 컨트롤: `[ PC ] [ Mobile ] [ PC+Mobile ]`.

- **PC**: 실제 Desktop 앱 Route 표시.
- **Mobile**: **실제 390px viewport**에서 동일 앱·동일 Route를 Phone Frame에 렌더링. 스크린샷/축소 CSS/별도 가짜 모바일 페이지 금지.
- **PC+Mobile**: 기본 `PC 67% : Mobile 33%`, Mobile Preview 오른쪽 배치, sticky 가능, PC는 컨테이너 폭에 맞춰 리플로우.
- 같은 Route/데이터/세션/권한/기록 공유. PC에서 이동하면 Mobile 동일 Route로 이동하며 Mobile에서 이동하면 PC도 적절한 동일 Route로 동기화. 내부 `guest`/`staff` 등 역할 특화 Route는 보안/권한 충돌 없이 적절히 Preview 정책을 정의한다.
- iframe Frame 안에서 재귀 프리뷰 금지, message origin/source 확인, Route Sync Loop 방지, 변경값 실시간/합리적 갱신.
- 실제 모바일 반응형과 Device View 둘 다 QA(390/430/768/1024/1280/1440/가능하면 1920). Phone Frame이 잘리거나 탭·Drawer·Bottom Nav·Safe Area가 망가지면 실패.
- 다른 시점/다른 데이터/다른 예약이 PC/Mobile에 동시에 표시되는 시연 오류는 P0 FAIL.

## 10. Role / 보안 / 데이터 최소화

- 데모 Role은 `이다플레이스 서비스관리자`, `이다컴퍼니 운영관리자`, `현장직원`, `체크인 고객(데모)` 4가지로 구분.
- 데모 Role Switcher는 실제 운영 보안이 아님을 명시한다. 상용 운영 전에는 Supabase Auth + RLS + server-side authorization, tenant isolation, 정보 접근 분리 검증이 필수다.
- 고객에게 직원용 메뉴·운영원가·다른 투숙객 정보·출입 관리 API Token을 노출하지 않는다.
- 검증 없는 고객 실명 검색 → 출입코드 공개 경로 금지.
- 보안 민감 이벤트(예약취소/PIN 회수/관리자 수동개입)에 감사로그, 접근제어, 위변조 방지와 오류 알림 구조를 둔다.
- **특히 최종 사용자가 숙소에 입실하지 못하는 상황을 피하기 위해 비상 입실/야간 연락 안내**를 UX에 포함한다. 만능 비상 PIN을 공개하지 않는다.
